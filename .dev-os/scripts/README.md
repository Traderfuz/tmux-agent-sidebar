# General Profile — Scripts

Reusable bash scripts inherited by every DevOS profile downstream of `general`
(webapp, cli, cloudflare-workers, pwa, installable-os, …).

Unlike `commands/`, `workflows/`, and `standards/` — which are consumed by the
DevOS template processor — scripts in this directory are **executable bash
files** meant to be copied into or referenced from project-level
`scripts/` directories.

## Convention

- All scripts use `#!/usr/bin/env bash` and `set -euo pipefail`
- All scripts support `--help` printing their own header comment
- Configuration is read from **environment variables** (never hardcoded),
  so projects can wrap or exec them without editing
- Every destructive or irreversible step has a corresponding `--skip-*` flag
- Every script has a `--dry-run` mode that prints what it would do

## Inheritance behavior

Because this directory lives in `general`, it is active in all 13 downstream
profiles via the inheritance chain: `default → general → <leaf profile>`.

A profile that needs a different implementation of `deploy-prod.sh` (for
example, a Cloudflare Workers profile that doesn't use Vercel) can override
it by placing its own `profiles/<leaf>/scripts/deploy-prod.sh` — the
distribution logic will prefer the leaf profile's version.

## Current scripts

| Script | Purpose | Key env vars |
|---|---|---|
| `deploy-prod.sh` | Full production deploy flow: pre-flight → prisma migrate status preflight → bounded prisma migrate deploy retry → vercel build → vercel deploy --prebuilt → smoke test. Auto-detects package manager (bun / pnpm / npm) from lockfile. | `DEPLOY_DOPPLER_PROJECT`, `DEPLOY_DOPPLER_CONFIG`, `DEPLOY_PROD_URL`, optionally `DEPLOY_PKG_MANAGER=bun\|pnpm\|npm` to override detection |
| `contract-impact-preflight.sh` | Shared contract-impact lifecycle port for planning, enforcement, reconciliation, and verification. Resolves one canonical target and delegates record mutation to the record engine. | `DEVOS_DIR` |

### Prisma migration safety (`deploy-prod.sh`)

When Prisma deploy is enabled, the script resolves one migration database URL before running any Prisma command:

- `DIRECT_URL` wins when present and is used for both `prisma migrate status` and `prisma migrate deploy`.
- `DATABASE_URL` is used as a fallback when `DIRECT_URL` is absent, with a visible warning because Supabase PgBouncer transaction-mode URLs can hang advisory-lock migrations.
- Both `migrate status` and `migrate deploy` run through bounded retry with exponential backoff, so one transient database connectivity failure does not abort the whole release.

This behavior lives only in the canonical profile script in this source repository. Installed runtime copies are generated by install/profile sync rather than tracked under `.dev-os/scripts/`.

### Package manager support (`deploy-prod.sh`)

Auto-detection precedence when `DEPLOY_PKG_MANAGER` is not set:

| Lockfile found | Detected as | Runner used |
|---|---|---|
| `bun.lockb` or `bun.lock` | `bun` | `bunx` |
| `pnpm-lock.yaml` | `pnpm` | `pnpm exec` |
| (none, or only `package-lock.json`) | `npm` | `npx` |

Override with `DEPLOY_PKG_MANAGER=<bun\|pnpm\|npm>` if auto-detection picks the wrong one (rare — usually indicates multiple lockfiles exist, which is itself a project smell).

A project that uses yarn classic should set `DEPLOY_PKG_MANAGER=npm` — yarn's `yarn exec` is compatible with the `npx` code path for prisma invocations and vercel doesn't care about yarn specifically. If a native yarn runner is ever needed, add a fourth case to the script.

## How a project uses these

### Option 1 — exec wrapper (recommended)

Project creates a thin wrapper at `scripts/deploy-prod.sh`:

```bash
#!/usr/bin/env bash
export DEPLOY_DOPPLER_PROJECT="myapp"
export DEPLOY_DOPPLER_CONFIG="prd"
export DEPLOY_PROD_URL="https://myapp.com"
export DEPLOY_HEALTH_PATH="/api/health"
exec ~/.dev-os/profiles/general/scripts/deploy-prod.sh "$@"
```

Benefit: the generic script is the single source of truth. Bug fixes in
`general/scripts/deploy-prod.sh` are picked up automatically by every
project wrapper.

### Option 2 — copy into project

For projects that want the script committed to their repo and locked to a
specific version:

```bash
cp ~/.dev-os/profiles/general/scripts/deploy-prod.sh ./scripts/
```

Benefit: the project is self-contained and the script version is frozen.
Downside: must be re-copied when the upstream version is updated.

### Option 3 — configured thin wrapper (between 1 and 2)

Project copies the script and **also** sets its config values hardcoded at
the top, replacing the env-var defaults. This is the pattern used by
`boxi-app-supabase/scripts/deploy-prod.sh` as of 2026-04-11. Useful when
the project wants to diverge in small ways (e.g. custom health check
response parsing) without losing the shape of the upstream script.

## Adding a new script here

1. Write the script using env vars for all configuration
2. Add a row to the "Current scripts" table above
3. Update `CHANGELOG.md` at the repo root under the general-profile section
4. Test against at least one downstream profile before committing
5. Bump the DevOS version if this introduces a new capability profiles
   depend on

## Anti-patterns

- **Hardcoding project-specific values** — always use env vars. If a value
  varies per project, it doesn't belong in a generic script.
- **Silent defaults for destructive actions** — never default `--skip-preflight`
  to true, for example. Destructive skips must be explicit.
- **Mixing business logic with deploy mechanics** — this directory is for
  deploy/build/migration plumbing, not application-level scripts.
